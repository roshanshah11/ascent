# Ascent V1 Roadmap — professional-grade, built for its own sake

*Researched 2026-07-18, revised same day after direction change: **this is not a product to sell**. Ascent is built for fun, but to a professional bar. The measuring stick: would a GNC/flight-dynamics engineer at a new-space or defense-tech startup — the people who run Basilisk, Nyx, and GMAT — respect this tool if they opened it? Every V1 decision is judged against that engineer, not against a customer.*

*Evidence labels: **[sourced]** = external, dated; **[local]** = this repo; **[inference]** = derived; **[bet]** = ambitious call.*

## The bar: what serious flight-sim tools actually do

What the new-space open-source stack established, and what Ascent must therefore match or beat:

- **[sourced]** [Basilisk](https://avslab.github.io/basilisk/) (CU Boulder/LASP) — the reference for professional sim architecture: **bit-for-bit repeatable Monte Carlo**, configurable-fidelity modular dynamics, 365× faster than realtime, hardware-in-the-loop mode, standalone Unity visualizer (Vizard), 2026 Docker workflow for reproducible GN&C simulation. Ascent already has the bit-for-bit property as a foundation, not a feature — that is rare company.
- **[sourced]** [Nyx](https://github.com/nyx-space/nyx) (Rust) — high-fidelity astrodynamics toolkit, **validated against GMAT**, flight-proven on CAPSTONE and Masten XL-1 trade studies. The credibility pattern: a new tool earns trust by publishing validation against the established baseline. Ascent's equivalent baselines: OpenRocket, RocketPy, real flight data.
- **[sourced]** [RocketPy](https://github.com/RocketPy-Team/RocketPy) — 6-DOF with variable-mass effects, ~1% apogee error validated against three university flights (peer-reviewed, J. Aerospace Eng.), weather from reanalysis/forecast/ensemble datasets, multi-stage, Monte Carlo dispersion. The physics bar for the rocketry domain specifically.
- **[sourced]** Supporting landscape: [OpenRocket](https://openrocket.info/) (design + 6-DOF, sounding-rocket class only), [CamPyRoS](https://campyros.readthedocs.io/) (wind variability, slosh), [OpenPost](https://github.com/bartkiewiczjacob/OpenPost) (aeroheating), JSBSim (general 6-DOF FDM), [OpenFOAM rocket toolchain](https://github.com/WyllDuck/OpenFOAM-ToolChain-for-Rocket-Aerodynamic-Analysis) / RASAero for aero databases. Startups like SpaceForest build in-house 6-DOF sims validated against their own flight data — the workflow Ascent should make unnecessary.
- **[sourced]** Market context (unchanged from first draft): incumbents bolt chat copilots beside the tool (Ansys/Siemens/Altair); AI-native players are cloud plays ([SimScale agents GA May 2026](https://www.simtool.com/article/simscale-launches-engineering-ai-agents-and-open-workflows-platform-for-autonomous-simulation-orches/), [Neural Concept $100M](https://www.engineering.com/neural-concept-launches-ai-design-copilot-at-ces-2026/), [Luminary](https://developer.nvidia.com/blog/faster-insights-from-luminary-clouds-engineering-simulations-with-nvidia-gpus/), [Flexcompute](https://www.flexcompute.com/flow360/)). Nobody has AI as a first-class client of one audited, offline, journaled command layer. That stays Ascent's identity.
- **[sourced]** [MCP spec 2026-07-28](https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/) finalizes in ten days: stateless core, **Tasks extension for long-running work**, MCP Apps. stdio transport is the desktop pattern. This is the standard rail for Pillar 3.

**[inference]** Ascent's positioning against this field: Basilisk/Nyx/GMAT are *libraries and toolkits for specialists* — powerful, no product surface, steep setup. OpenRocket is a product but hobby-grade physics and architecture. Ascent's empty seat: **Basilisk-grade rigor (repeatable MC, validation discipline, modular fidelity) inside a real workbench (model tree, studies, evidence, undo, GUI) that an AI agent can operate.** No one occupies that seat.

## The V1 definition

**V1 = the tool a flight-dynamics engineer would choose for a sounding-rocket-class vehicle campaign**: model the vehicle, run repeatable 6-DOF dispersions, check structural and stability margins, generate the evidence report, reconcile against flight data — with an AI copilot operating through the audited seam the whole way. Professional means: physics validated against named baselines, architecture that doesn't rot, format stability, real docs, signed builds.

Five pillars. No sales, no wedge, no customers — capability and craft only.

## Pillar 1 — Physics depth (match RocketPy, then pass it)

- **v0.4** Land 6-DOF (Codex step 6) as the high-fidelity engine; 3-DOF stays the fast engine. Cross-engine consistency tests (same vehicle, 3-DOF vs 6-DOF apogee within stated tolerance) become part of the suite.
- **v0.4** Multi-stage vehicles + separation events in the model tree. Variable-mass effects done properly (RocketPy's differentiator **[sourced]**).
- **v0.5** Real atmosphere: wind/density profiles imported as data files (GFS/radiosonde/ensemble) — hashed into the study input hash, no runtime network. Full descent: drogue/main staging, drift, landing dispersion under the imported wind.
- **v0.5** Structural margin pack: fin flutter, thrust loads, rail-departure velocity — the checks a flight-readiness review runs.
- **v0.6** **Validation library as a feature**: bundled public flight datasets, one-click "run Ascent against known flight, show the error," results feed the credibility scorecard. This is the Nyx-validates-against-GMAT pattern **[sourced]** productized. Target: match RocketPy's ~1% apogee class on the same flights.
- **v1.0 [bet]** Study-kind expansion toward GNC territory: TVC/control-law hooks in 6-DOF (the Rust [rocket-sim](https://github.com/ZenAlexa/rocket-sim) proves feasibility), stability-derivative sweeps, optimization studies ("max apogee s.t. stability > 1.5 cal") — gradient-free first, surrogate-gradient later ([JAX surrogate pipelines](https://arxiv.org/html/2604.22087v1) **[sourced]**).

## Pillar 2 — Geometry & data out

- **v0.5** STL/STEP export from the model tree (fin cans, nose cones, rings). `as_built` measured-mass overrides as first-class params — journal records the design-vs-hardware reconciliation OpenRocket users do by hand **[sourced]**.
- **v0.6** Deterministic report generation: dimensioned fin templates, CG/CP airframe layout, and the full evidence report (Pillar 4) as PDF/HTML.
- **v1.0 [bet]** OpenUSD scene export; standalone visualizer path à la Basilisk's Vizard **[sourced]** if the in-app viewport hits limits.

## Pillar 3 — AI-native operation (the identity)

- **v0.4** **`ascent-mcp`** (stdio): wraps the existing seam — `get_document`, `propose_commands`, `apply_proposal`, `run_study`, `read_evidence` as MCP tools; adopt the Tasks extension for long-running dispersions once 2026-07-28 finalizes **[sourced]**. Zero LLM inside Ascent; offline/deterministic constraint holds.
- **v0.5** Agent evals in CI: scripted agent sessions with golden outcomes ("agent asked to widen fins must surface `studies_made_stale`"). The seam gets regression-tested like physics.
- **v0.6** In-app approval surface: render an external agent's proposal (diff, stale warnings, approve/reject) as a panel. Ascent draws the approval UI; the brain stays outside.
- **v1.0 [bet]** Journals as corpus: every session is a byte-identical operator trace. Publish an eval harness — "can your agent fly this mission in Ascent?" Because for-fun doesn't mean invisible; this is the artifact that shows the seam works.

## Pillar 4 — Evidence & trust artifacts

- **v0.5** Flight-readiness report: one deterministic document — vehicle spec, stability across the burn, dispersion ellipse, structural margins, credibility scorecard, every number hash-linked to its study.
- **v0.6** Flight-data reconciliation: import altimeter CSV (PerfectFlite/RRC3/Blue Raven), overlay predicted vs actual, error metrics into the scorecard. Predict → fly → reconcile is the loop no rocketry tool closes **[inference]**.
- **v1.0** Format stability: schema migration guarantees (schema_version exists **[local]**), journal grammar + project format + copilot contract published as versioned, documented interfaces.

## Pillar 5 — Experience: the workbench as the demo

*The ambition target: the UI itself is proof of the architecture. Luminary demos a real-time virtual wind tunnel on Omniverse **[sourced]**; Basilisk ships a standalone Unity visualizer **[sourced]**. Ascent's answer is stronger because the physics is local, deterministic, and journaled — every visual is a rendering of provable state, not a movie. The bar for V1 is not "professional viewport"; it is "the clip a Basilisk user stops scrolling for."*

- **v0.4** Step 10 workbench shell: dockable panels, Design/Simulate/Results/Review workspaces, command palette (fuzzy-search over the text grammar — nearly free **[local]**), keyboard-first, dark mission-control visual language done properly (typography, spacing, motion) — not engineer-gray Qt.
- **v0.5** wgpu viewport as the centerpiece, not a widget: instanced rendering of the **full dispersion ensemble** — 1,000+ trajectory ribbons live, percentile shells, landing ellipse on a terrain plane (launch-site DEM tiles imported as hashed data files, offline like everything else). 6-DOF attitude visible: the vehicle *flies*, weathercocks, coasts, tips — not a dot on a polyline.
- **v0.5** **Physics-in-the-loop direct manipulation**: drag a fin's span in the viewport → debounced fast-engine re-sim → CP/CG markers and stability margin move *while you drag*. Release = one journaled command. Direct manipulation and the command spine are not in tension — the drag is preview, the drop is dispatch. This is the "wind tunnel feel" **[bet]** on local hardware.
- **v0.6** **Timeline scrubber as the spine of the app**: one global time cursor synced across viewport, plots, and event strip (ignition, burnout, apogee, deploy). Scrub anywhere, every view follows. Flight review becomes cinematic: chase cam, pad cam, onboard cam presets.
- **v0.6** **Journal cinema** — the signature feature: replay any session journal as an animation of the *design process itself*. Watch the vehicle grow part by part, studies go stale and re-verify, the copilot's batches land. Nobody else can build this — it falls out of byte-identical replay **[local]** — and it doubles as the provenance audit view.
- **v0.6** **Ghost proposals**: an agent's pending batch renders as overlay geometry — proposed fin in translucent accent color next to current fin, stale studies pulsing in the tree, diff summary docked. Approving a change means *seeing* the change. This is the approval UI (Pillar 3) done as graphics, not as a JSON dump.
- **v1.0** **GPU-resident dispersion in V1, not after**: 10k-flight Monte Carlo on wgpu compute, byte-identical to the CPU path, verified in CI — interactive ensemble exploration (brush a percentile band, see which seeds/winds produced it). The determinism-on-GPU claim nobody else even attempts becomes the V1 headline demo.
- **v1.0** Design-space canvas: studies as cards with sparkline results, drag to compare, overlay ensembles from two designs in one viewport (A/B the vehicle, visually).

### Craft substrate (correct the first time)

- **Workspace discipline [sourced]**: flat crate layout, virtual root manifest, crate = folder name ([matklad's large-workspace rules](https://matklad.github.io/2021/08/22/large-rust-workspaces.html)); no crate under ~500 lines with one dependent; automation as `cargo xtask`; MSRV pinned; `cargo audit`/`cargo vet` in CI; Cargo.lock committed. Public-API discipline: `pub` is a promise — internal crates stay `0.0.0`, exports curated (already the pattern **[local]**).
- **The standing invariants** (already law, now written): every mutation through the one dispatcher; journal replays byte-identically; golden pin green every commit; no runtime network; zero deps without justification; no placeholder code — each step lands tested and complete or doesn't land. **The render layer dispatches zero commands** — viewport/scrubber/cinema consume snapshots and journals only; drags dispatch exactly one command on release.
- **v0.6** Distribution like real software: signed/notarized macOS + Windows builds, Tauri auto-update, reproducible-build documentation (the 2026 Basilisk Docker-reproducibility direction **[sourced]**), versioned docs site with journal grammar + copilot contract as the API reference.
- **v1.0** Extension seam ([Blender's model](https://code.blender.org/2022/10/blender-extensions-platform/) **[sourced]**): manifest + permissions, extensions add StudyKinds/exporters/part libraries **through the command layer only** — the no-second-mutation-path invariant extends to plugins. Local repository only; no store, no federation — this is for fun.

## Non-negotiables carried forward

Determinism (same seed → same bytes) survives every pillar, GPU included. One command layer — GUI, console, CLI, MCP, extensions dispatch the same stream. No runtime network; external data enters as hashed files. Golden pin green every commit. Validation against named baselines (OpenRocket, RocketPy, real flights) before any physics claim. Nothing ships half-done to be "fixed later."
