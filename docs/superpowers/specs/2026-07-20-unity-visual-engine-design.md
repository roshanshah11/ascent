# Unity Visual Engineering Runtime Design

**Status:** Approved 2026-07-20

## Product thesis

Ascent is a visual engineering runtime for constructing, simulating, interrogating, and reviewing complex aerospace systems. Cinematic quality is not decoration: scale, motion, separation, uncertainty, and temporal relationships become easier to understand when the presentation is spatially credible and visually legible.

The first proof is intentionally narrow: one evidence-graded NASA Black Brant IX reference mission, simulated by Ascent's Rust core and reviewed from launch through landing in a convincing Unity experience. It must feel like professional aerospace software, not a game, a generic mission viewer, or a collection of disconnected UI panels.

The slice answers one question: can Unity provide the visual quality and interaction speed Ascent needs while preserving the deterministic, evidence-backed Rust architecture?

## Product decisions

- Unity 6 LTS with HDRP is the visual client.
- Rust remains authoritative for physics, mission state, evidence, trace generation, and AI command seams.
- Unity begins as a read-only visualizer. It may gain authoring only after the measured platform gate.
- The first supported vehicle is NASA Black Brant IX, reconstructed from public primary sources.
- The first experience is launch-to-landing review, not a general scenario editor.
- Tauri and React remain intact during the experiment.
- `ascent-mcp` remains intact for external agents and is not reused as the visualization transport.
- Interactive and cinematic output are separate quality tiers.
- Global terrain, orbital-scale worlds, and Cesium are deferred.

## The narrow convincing experience

The operator launches Ascent Unity and starts the checked-in Black Brant IX reference mission. Unity supervises the Rust bridge, receives a deterministic trace, and reveals the vehicle on a bounded White Sands launch range. The operator can play, pause, scrub, step, reverse-seek, change rate, jump to named events, and move between pad, chase, onboard, ground-tracking, and inspection cameras.

The default view is cinematic and restrained. Engineering layers can reveal trajectory, velocity, body axes, attitude, stage state, named events, and uncertainty when the trace contains it. Selecting a time shows trace-backed values with units and evidence status. One clean-view action hides every engineering overlay without altering time, camera, or mission state. A cinematic export produces both imagery and a machine-readable manifest.

This is complete when a technically literate viewer can understand what happened, when it happened, how the vehicle was oriented, which stage was active, and where every displayed engineering value came from.

## Authority boundary

Rust owns the mission document, simulation clock, state transitions, events, evidence, validity masks, and canonical trace hash. Unity owns rendering, camera state, user playback state, layer visibility, presentation interpolation, and export.

Unity must not:

- integrate its own scientific trajectory;
- use Unity physics to determine vehicle transforms or separation truth;
- mutate an Ascent project;
- infer missing samples across invalid intervals;
- invent engineering values from rendered geometry;
- dispatch commands through MCP.

## Runtime architecture

Add two Rust workspace crates:

- `crates/ascent-visualizer-protocol`: versioned messages, framing, fixtures, and trace validation contracts.
- `crates/ascent-visualizer-bridge`: a read-only `ascent-visualizer-bridge --stdio` child process using existing Ascent crates.

Add the Unity project at `visualizer/AscentUnity/`. C# launches and supervises the bridge with `System.Diagnostics.Process`, writes framed requests to `StandardInput.BaseStream`, reads framed responses from `StandardOutput.BaseStream`, and treats stderr as diagnostics only. No listener, socket, C ABI, or MCP transport is introduced.

## Protocol v1

Every frame is a four-byte little-endian unsigned payload length followed by UTF-8 JSON. The maximum payload is 16 MiB. Every envelope contains:

- `protocol_version`
- `message_id`
- `request_id`
- `kind`
- `payload`

Client request kinds are `hello`, `list_missions`, `run_mission`, `cancel_run`, and `shutdown`.

Server message kinds are `hello_ack`, `mission_catalog`, `run_started`, `run_progress`, `trace_manifest`, `trace_channel_chunk`, `trace_events`, `run_completed`, `run_cancelled`, and `error`.

The initial mission catalog contains only `nasa.black-brant-ix.reference`. Trace channel messages contain at most 1,024 samples. The bridge emits channels in canonical order with contiguous sequence numbers and a canonical SHA-256 identity. Unity accepts a trace only after all declared channels and events arrive and validate.

Protocol fixtures are generated by Rust and consumed unchanged by Unity tests. Duplicate message ids, stale process generations, malformed JSON, invalid UTF-8, oversized frames, missing or out-of-order chunks, unknown required fields, and hash-invalid traces fail closed with an actionable error.

## Lifecycle

- Handshake timeout: five seconds.
- Graceful shutdown timeout: two seconds.
- Automatic restart: one attempt after an unexpected bridge exit.
- Every launch increments a process generation; stale output is ignored.
- Cancellation returns the client to a state from which a new run can begin.
- Unity exit reaps the child process.

## Coordinates and playback

Rust trace positions use launch-local East-North-Up metres. Unity uses `X = East`, `Y = Up`, and `Z = North`, with one metre equal to one Unity unit. Attitude conversion uses a complete basis matrix; quaternion components are never manually swapped.

Position uses linear interpolation between adjacent valid samples. Attitude uses normalized shortest-path spherical interpolation. The client never interpolates across invalid or absent samples. Event jumps use exact Rust event timestamps. Playback rates are 0.25x, 0.5x, 1x, 2x, and 5x.

## Visual system

The Unity project uses Unity 6 LTS, HDRP, Cinemachine, Timeline, VFX Graph, UI Toolkit, Unity Test Framework, Splines, and the official Newtonsoft JSON package.

The bounded White Sands environment uses an offline, rights-cleared USGS terrain subset. The Black Brant IX model uses reproducible geometry, physically based materials, separable stages, markings derived from rights-cleared NASA imagery, and explicit notes for visual approximations. Lighting, atmosphere, shadow, haze, plume, and camera motion favor physical legibility over spectacle.

The application shell is a professional review surface: semantic timeline along the bottom, mission and bridge status, compact layer controls, state inspector, camera selector, evidence labels, and actionable failure states. It avoids game HUD language, decorative gauges, excessive bloom, and untraceable readouts.

## Evidence contract

Every sourced artifact records source URL, retrieval date, SHA-256, rights, affected fields, and one grade: `authoritative`, `derived`, or `approximate`. Derived values record their formula and inputs. Approximate values state their effect on the reference scenario.

Every engineering value displayed in Unity resolves to one trace channel, typed event, or evidence record. The reference trace is not presented as a reconstruction of a historical NASA flight.

## Quality tiers

Interactive acceptance is 1920x1080 at no less than 30 FPS in the Unity editor and 45 FPS in a packaged macOS build on the M3 Pro with 18 GB memory, without sustained macOS memory-pressure warnings.

Cinematic output may render offline. Its manifest records trace hash, protocol version, mission id, camera, time range, quality preset, resolution, frame rate, Unity version, and evidence caveats.

## Platform gate

Unity expands beyond a visualizer only if:

- the complete experience is materially more legible and impressive than the current viewport;
- local interactive targets pass;
- a repeat run produces the same canonical trace identity;
- process failure and cancellation recover cleanly;
- every engineering overlay remains traceable;
- the Rust authority boundary stays intact;
- the review workflow feels coherent enough for an aerospace engineer to use without a guided demo.

If the gate fails, Unity remains an optional visualization and cinematic-export client. Tauri, React, MCP, and the Rust core remain in place in either outcome.

## Explicit exclusions

- General vehicle or mission authoring in Unity
- AI proposal or approval UI in Unity
- Global Earth, Cesium, streamed terrain, or runtime asset downloads
- Orbital flight, TVC, powered landing, or SpaceX-class behavior
- Historical-flight equivalence claims
- Network or remote bridge transport
- Installers, signing, cloud rendering, or collaboration
- Production marketplace assets without verified redistribution rights
